# RVM 整网上 NPU：异构层串联实验（hetero spike）

日期 2026-11-11，分支 `phase2-npu`，未提交。接 `rvm-npu-chain-spike.md`（同形状 N 层）。
代码：`npu/chain_hetero.py` + `npu/kernels/conv_generic.cc`（都是新文件，没改已有文件）。

## 结论（一句话）

**可行，过判据，但有三处要带进下一步的限制。** 一个通用内核（形状由权重头部的运行时描述符决定）+ 固定大小的 fifo 元素，
在一次 NPU 调用里串起 3×3 s1 / 3×3 s2 / 1×1、两种分辨率（180×320、90×160）、两种通道数（16、32）的层，
所有组合（1–18 层）都与 numpy 整数参考**逐字节一致**；每层额外开销 **约 0.04–0.075 ms**（判据 ≤ 0.1 ms）。

## 做法

- 四种层：A = 3×3 s1 16→16 @180×320，B = 3×3 s2 16→32 → 90×160，C = 1×1 32→32 @90×160，D = 3×3 s1 32→32 @90×160。
- **一个内核** `convGenericLine(r0, r1, r2, wts, out)`：权重块头 64 B 是描述符 `[ICB, OCB, WT, stride, k, shift]`，
  内核运行时分三条路（3×3 s1 / 3×3 s2 / 1×1），ICB、OCB、WT 都是运行时循环边界。
  s2 用 `filter_even/filter_odd(…, 8)`（8 字节 = 1 像素）拆奇偶像素，全部对齐加载，没碰 llvm-aie 的非对齐常量偏移 bug。
- **固定大小的 fifo 元素**（编译期只有一种）：
  - 输入 = `[ICB_max][PLANE_max]`：fill 的 TAP 每块读 PLANE_max 字节、读 ICB_max 块，多出来的是邻近像素或下一行的垃圾，内核不看；
    DDR 缓冲区尾部留余量。**输入端可以随便多读。**
  - 输出 = `OCB·WT·8` 字节，**必须所有层相等**（drain 会把垃圾写进 DDR，所以输出不能带垃圾）。
    这里通过每层选宽度切条让它恒等于 2560（2 块×160 = 4 块×80）。
  - 权重 = 64 + 最大层权重，主机侧补齐。
- 激活仍是整幅带边布局 + TAP；**每种形状单独两个 scratch 槽**（不同形状共用槽会把上一层的内部像素留在下一种形状的"边"上）。
- core 侧：相邻且（行数, stride）相同的层合成一个 `range_` 循环；1×1 也按 3 行窗口喂（多读上下两行），fifo 用法统一。

## 踩到的坑：IRON 1.3.4 ObjectFifo 下降 bug（会挂死）

stride 2 的滑窗写成 `acquire(3) … release(2)`，如果它前面还有一个 `range_(≥2)` 的层循环（如 `A,A,B`），
下降后的行循环**没有剥第一次迭代**，每次迭代都按"再取 3 个"上锁（应为 2）→ 多等 1 个对象 → `ERT_CMD_STATE_TIMEOUT`。
`A,B`、`B,C,C`、`B,D,C,D,C,D` 都正常，只在这种组合下出现；看 `input_with_addresses.mlir` 的 core 能直接看到
`AcquireGreaterEqual, 3` 出现在循环体里。把层循环展开（不分组）也能好。
**绕法（已用）**：s2 层不让相邻窗口共享行，由 DMA 给每个输出行发完整 3 行（TAP `[R, 3, ICB, PLANE]`，
步长 `[2·行, 行, 块, 1]`），core 每行 `acquire 3 / release 3`，循环边界持有数恒为 0。代价：s2 层 DMA 读量 ×1.5。
s1 的 `acquire 3 / release 1` 滑窗在所有组合里都没问题。

## 数字（7840HS，每点 100 次取中位；这一轮机器比上次忙，主机 CPU 也偏高，中位噪声大，最快值更可信）

| 链 | 层数 | 中位 ms | 最快 ms | 主机 CPU ms/次 |
|---|---|---|---|---|
| A | 1 | 0.67 | 0.56 | 0.23 |
| B | 1 | 0.66 | 0.53 | 0.26 |
| A,B,C,D | 4 | 1.66–1.70 | 1.36 | 0.40–0.47 |
| A,A,B,D,C,D | 6 | 2.25 | 1.94 | 0.43 |
| A,B,(C,D)×4 | 10 | 3.06 | 2.49 | 0.57 |
| A,B,(C,D)×8 | 18 | 4.23 | 3.78 | 0.53 |
| A×10（通用内核） | 10 | 4.52 | 4.07 | 0.83 |

**每层额外开销**（reps 法：内核每行重复 1/2/3 次，斜率 = 纯计算，截距 = 固定 + Σ每层额外；固定按 0.25 ms）：

| 链 | 纯计算 ms | 截距 中位 / 最快 | 每层额外 中位 / 最快 |
|---|---|---|---|
| A,B,C,D | 1.06 | 0.41 / 0.42 | 0.04 / 0.04 |
| A,B,(C,D)×4 | 1.82 | 0.86 / 0.71 | 0.06 / 0.05 |
| 从 4 层到 10 层的增量（6 层 C/D） | | | 0.075 / 0.048 |
| A×10 | 3.15 | 1.00 / 0.62 | 0.075 / 0.04 |

→ 每层额外开销 0.04–0.075 ms，过判据；比同形状的 0.043 略高或持平（主要是噪声，形状切换本身看不出额外代价）。

**通用内核的代价**：A 层纯计算 0.315 ms/层（专用 `conv3x3.cc` 是 0.193），只有专用版的 61%（约 420 GMAC/s）。
原因是 ICB/OCB/WT 都成了运行时循环边界、不能全展开。可以给最常见的几种 ICB 做编译期特化分支，但要和程序内存（下一条）权衡。

## 要带进下一步的三个限制

1. **core 程序内存（16 KB）装不下按形状展开的层循环。** 实测内核本体约 3.3 KB；core 上每多一个层组（行数或 stride 不同）
   多 0.7–1.5 KB → 大约只够 10 组。RVM 85 层形状变化多，**必须让 core 的层循环也由描述符驱动**
   （行数、stride 从权重头读出来当 `range_` 的运行时边界；ObjectFifo 下降本来就是带运行时计数器的动态版，应该可行）。
   这是下一个 spike 的首要问题。
2. **输出元素大小必须所有层相等。** 这里靠宽度切条凑成 2560。真实网络通道 16–960、分辨率多档，要么每个输出行拆成
   若干个固定块（kernel 一次产出一块、core 每行 acquire 多次），要么按层改切条/切段数。要先把 RVM 85 层的
   (OC, W_out) 表拉出来看能不能统一成一种块大小。
3. **s2 层要绕 ObjectFifo 下降 bug**（上面），DMA ×1.5；如果改成描述符驱动的通用循环，要重新确认这个 bug 不会在别的形态下冒出来。

## 对整网的推算（修正）

额外开销 85 × 0.05–0.075 ≈ 4–6 ms；计算 1.84 GMAC 按通用内核 ~420 GMAC/s ≈ 4.4 ms，小层/1×1/depthwise 效率更低；
加固定 0.25 ms → **约 9–12 ms/帧**（比上次按专用内核估的 7–9 ms 高）。拉回来的手段：常见形状的编译期特化分支、
把逐元素算子融进卷积尾部减少层数、1×1 层不再按 3 行窗口喂（省 DMA）。

## 复现

```bash
source npu/env.sh
python -m npu.chain_hetero --iters 100                  # 全部组合的正确性 + A,B,(C,D)×K 拟合 + A×N 对照
python -m npu.chain_hetero --spec A,A,B,D,C,D           # 单条链
python -m npu.chain_hetero --compute A,B,C,D            # 纯计算 / 额外开销拆分
```
