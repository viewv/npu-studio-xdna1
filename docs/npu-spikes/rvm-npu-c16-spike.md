# RVM 整网上 NPU：固定大小输出块 + 每 core 行数 + 全描述符驱动的 core（c16 spike）

日期 2026-11-11，分支 `phase2-npu`，未提交。接 `rvm-npu-desc-loop-spike.md`。
代码：`npu/chain_c16.py` + `npu/kernels/conv_c16.cc`（新文件）。

## 结论（一句话）

**desc-loop spike 留下的两个结构问题都解决了，core 循环也彻底和形状无关了。** 13 层 RVM 编码器形状的链
（180×320 → 90×160 → 45×80 → 23×40 → 12×20，OC 16–128，3×3 s1/s2 + 1×1）以及 25 层的加长版都与参考**逐字节一致**，
包括 23+22、6+6+6+5 这种不均分的行、12×20 存成 40 宽（补宽列检查过全是零）。core 程序 `.text` ≈ **4.7 KB，恒定**
（内核三条分支 + core 两段，和层数、形状、类别都无关）。每层额外开销 **约 0.056–0.069 ms（最快值）**，中位噪声大。

## 关键发现：ObjectFifo 运行时次数循环的规则

（之前 dyn 模式被拒是因为这个，现在弄清楚了）
- acquire/release 可以放进**运行时次数**的 `range_`，**只要循环体相对于进入时的持有数是平衡的**。
- stride 1 滑窗：循环前 `acquire(2)`，循环体 `acquire(3) … release(1)`（净 +1 −1），循环后 `release(2)` → 行数可以是运行时值。
  （desc-loop spike 的 dyn 失败是因为进入时持有 0、第一次迭代要取 3，不平衡）
- stride 2：每行 `acquire(3)/release(3)`；输出块：`acquire(1)/release(1)`。都平衡。
- 外层用 `range_(0/1)` 选段，段内进出持有数为 0。
→ **core 上只有 s1、s2 两段代码，行数、每行块数、是否参与这一层，全部从权重头读。** desc-loop 的"类别"不需要了。
在 chain_hetero 上也验证过（临时改动，已撤回）。

## 做法

- **16 通道像素布局** `[H+2][CP][PAD+Ws+PAD][16]`：输出块 = 1 个通道组 × CW(40) 像素 = 640 B，是 DDR 里连续的一段；
  一行输出 = OCP × (WT/40) 个块，drain 的 TAP 还是 `[行][通道组][WT·16]`。**所有层输出 fifo 元素都是 640 B。**
- 内核每次调用算一个块（块号 j 由 core 的循环变量传进去）；`mmul<4,8,8>` 的 A 用 `interleave_unzip(·, 8)` 从 4 像素×16 通道拆成
  低/高 8 通道（等价于 `mmul<4,16,8>` 内部做的事，但拆一次喂 2 个输出块）。stride 2 用 `filter_even/odd(·, 16)`。
- **补宽**：存储宽度 Ws 补到 40 的倍数，内核把 ≥ 本 core 真实宽度（描述符按 core 给）的输出写 0 → 补出来的列就是下一层的零填充。
- **每层自己选切分**：宽 t 条 × 高 4/t 段（取补宽最少的），行数余数分给前几段；不满 4 个 core 的层，空闲 core 选择字节为 0。
- **输入元素固定 6144 B** = `[ICP_pad][PLANE]`，每层 PLANE = 6144/ICP_pad（≥ 真实条带，≤ 4064 B 以内），多读的是垃圾。
- 权重头 128 B：int32 `[ICP, OCP, WT, s, k, shift, NXC, PLANE]` + 每 core 16 B `u16 [rows, sel_s1, sel_s2, wvalid, 每行块数]`。
- shim BD 最高维（迭代维）上限 64：stride 2 的 fill `[行, 3, ICP, PLANE]` 行 > 64 时拆成几个 fill。

## 数字（7840HS，100 次取中位；机器负载 ~2，中位抖得厉害，看最快值）

| 链 | 层数 | GMAC | 中位 ms | 最快 ms | 主机 CPU ms/次 |
|---|---|---|---|---|---|
| e1（3×3 s2 16→16 180×320） | 1 | 0.033 | 0.80–0.85 | 0.67 | 0.25 |
| head（e1–e3） | 3 | 0.114 | 1.72–1.78 | 1.23 | 0.33–0.54 |
| enc（e1–e13） | 13 | 0.197 | 2.07–3.02 | 1.82–1.86 | 0.38–0.64 |
| low（enc + 12×20 三层 ×4） | 25 | 0.214 | 2.63 | 2.27 | 0.58 |

reps 拆分（最快值）：enc 纯计算 0.87 ms、截距 1.15 → 每层额外 ≈ 0.069 ms；low 纯计算 0.85、截距 1.66 → ≈ 0.056 ms。
enc→low 多出的 12 个 12×20 小层只多 0.41 ms（最快）→ **小层每层 ≈ 0.034 ms**（含计算）。
比同形状实验的 0.043 略高：每行拆成多个 640 B 块，每块一次 acquire/release + 内核调用。

## RVM 85 层按现在的方案归类（`rvm_convs_180x320.tsv`，通道补到 16 的倍数，权重预算 18 KB/core）

| 类 | 层数 | MMAC | 占比 |
|---|---|---|---|
| **现在就能跑**（3×3 / 1×1，输入元素和权重都放得下） | 26 | 1026 | 55.8% |
| 权重太大 → 要按 OC 分块（如 Conv_92 80→480、Conv_176 3×3 128→128，都在 12×20） | 9 | 368 | 20.1% |
| 输入行太大 → 要按 IC 分块（240–960 → 80–160 的 1×1，12×20；多数权重也大） | 14 | 399 | 21.7% |
| depthwise 3×3 / 5×5（含 s2、dilation 2） | 19 | 42 | 2.3% |
| SE 全连接（1×1 分辨率） | 17 | 1.6 | 0.1% |

## 下一步

1. **OC / IC 分块**（42% 的计算在这里，全是 12×20 的高通道层）：
   - OC 分块：权重流按 ocp 组切成固定大小的元素，每组把同一批输入再喂一遍（12×20 的输入很小，重复读不贵）；
   - IC 分块：1×1 层的部分和留在内存（int32），按 IC 块累加，最后一块再量化输出；或者把宽度切得更细，
     让 [全部 IC][8–16 像素] 放进一个输入元素（1×1 不需要水平窗口）。
   两种都要动描述符格式，所以先做。
2. depthwise 3×3 / 5×5 / s2 / dilation 2 分支（计算量小，但 19 层的固定开销要压住）。
3. 3×3 特化提速（3×3 占全网 73% 计算，通用内核只有专用版 61% 的速度）。
4. SE、hardswish、Add、Concat、Resize、ConvGRU。
