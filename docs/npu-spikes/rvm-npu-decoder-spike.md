# RVM NPU：解码器（进行中）

接 alpha spike。功耗对比（overhead spike 末尾）说明整网上 NPU 预计比 780M 每秒省约 2 W，所以开始做解码器。

## 第一步：结构 + 浮点参考 + 量化方案（已完成）

- 解码器的完整数据流见 `npu/rvm/decoder_ref.py` 文件头：LRASPP → decode4（GRU）→ decode3..1（双线性 ×2 + 三路拼接 + 3×3 + GRU）
  → 全分辨率两个 3×3 + 1×1 投影 → DGF 细化。浮点参考连续 20 帧和 onnxruntime 最大差 ~1e-6。
- downsample_ratio = 1 时 DGF 细化不是恒等，和不细化的 alpha 在边缘差到 0.35 → NPU 版也要做。
- 量化方案（`npu/rvm/decoder_q.py`，伪量化）：GRU 状态固定 1/127、sigmoid / tanh 整层查表、上采样整数 3:1 加权、
  DGF 的 box 和乘积在 int32 里算。只看解码器，对浮点 alpha 的边缘带误差 1.05/255、MAE 0.08（编码器自己是 2.4/255）。
  细节和对照表在 skill 的 `references/quant.md`。
- 坑：伪量化里特征不量化（enc='float'）会让权重量化把其他输入通道压成 0，看起来像方案不行（边缘带 27–68），其实是模拟的 bug。

## 第二步：双线性 ×2 上采样（已完成）

- 新层类型 `Layer(op=2, oh=…)`，复用 s1 滑窗段，每个输入行窗口出 2 个输出行；整数 `(9c + 3n + 3c' + n' + 8) >> 4`（= 双线性四舍五入），
  和 `decoder_ref.up2` 四舍五入后完全一致。4 个真实形状（含 12→23、23→45 裁行、四边夹住）第一次就逐字节一致；`check` 加了 `up` 链（23/23）。
- **程序内存到顶了**：加上上采样后所有分支一起编约 16.0 KB，链接后 `.text` 16304 / 16384 B。
  第一版把分派逻辑写在入口函数里，入口变大后编译器不再内联 `conv1`，又多了 0.7 KB；两个运行时除法（j 拆成子行 / 组 / 块）各占几百字节，换成比较和移位。
- 解决办法：**按链编译**（`Plan.kernel_flags()` → `-DNO_xxx`），编码器 ≈ 14.9 KB、解码器类 ≈ 7.5 KB。代价是编码器和解码器要分两次调用（+~0.25 ms）。

## 第三步：通用存储布局（多路拼接 / 就地写 / 外部输入 / 分段调用，已完成）

解码器的数据流需要的不只是"三路拼接"：
- `[上采样 ‖ f_k ‖ s_k]` 里的 f_k 是编码器输出 → 编码器要把 f_k **直接写进解码器的存储**（同一个 Plan 管全网放置）；
- GRU：ih 读 `[b ‖ h]`、hh 读 `[r·h ‖ b]`、更新读 `[h ‖ r ‖ z ‖ c]` 再**原地写回 h**（下一帧接着用）；
- 解码器还要主机给的原图 src。
于是把 `Layer.cat`（只能两路、只用于残差）推广成：`Layer.nx`（输出紧跟在某个张量后面，可以往后指）、窗口读（`ic` 大于源张量就连着读）、
`Layer.al`（就地写）、`Layer(op=3)`（外部输入）、`C16Chain(parts=…)`（一个 Plan 分几次调用）。
测试链 `cat3`、`alias`、`cat3` 分两次调用都逐字节一致，`npu.check` 26/26；编码器最快 9.39 ms（没变）。

GRU 一级的存储排法（计划）：`[r·h ‖ b ‖ h ‖ r z ‖ c]`（ih 读 b‖h，hh 读 r·h‖b，逐元素乘读 h‖r，更新读 h‖r‖z‖c 忽略 r、写回 h）；
x 卷积的 a / b 拆成两层（a 单独放，b 放进上面的存储）；上采样也拆成 up(a)、up(h') 两层写进下一级的 `[up_a ‖ up_h ‖ f ‖ s]`。

**意外**：分段调用每多一段要多约 1.5 ms（cat3 0.48 → 1.90 ms，mnv3r 5.78 → 7.37 ms），因为每段是不同的 xclbin，调用时要重新加载硬件配置。
编码器 + 解码器分两次调用可以接受（30 fps 预算 33 ms），但长远要把代码压回一次调用：例如首层 3×3 s2 改成主机做 space-to-depth 后的 s1（省掉 conv3s2 1.4 KB）、
dw 模板合并、SE 池化瘦身。
