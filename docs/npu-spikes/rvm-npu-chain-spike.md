# RVM 整网上 NPU：串联验证实验（chain spike）

日期 2026-11-11，分支 `phase2-npu`，未提交。代码：`npu/chain_spike.py`（新文件，内核复用 `npu/kernels/conv3x3.cc`，未改任何已有文件）。
`python -m npu.check` 8/8 ✅。

## 结论（一句话）

**可行，过判据。** 一次 NPU 调用里串 N 层 16→16 3×3 卷积（180×320），每层**额外开销约 0.035–0.05 ms**（判据 ≤ 0.1 ms），
1/2/5/10/20/40/85 层全部与 numpy 整数参考**逐字节一致**；主机 CPU 时间每次调用 0.14–0.35 ms，**基本与层数无关**。

## 做法（编过、能跑的 IRON 写法）

- **一个 runtime sequence，每层一个 task group**：`fill 权重(偏移 k·n_w) + fill 激活(TAP) → drain(TAP, wait=True) → finish_task_group`，
  Python 里 `for k in range(N)` 展开。层间依赖靠 drain 的 wait 做屏障。N=85 也照样编译（~2 s JIT），没碰到 BD/指令数上限。
- **worker 在 core 上循环层**：`for _ in range_(N): acquire 权重; for _ in range_(rows): 3 行滑窗…; release(2); release 权重`。嵌套 `range_` 没问题。
- **激活全在 DDR、层间零主机参与**：所有层用同一种"整幅宽度带边"布局 `[H+2][ICB][PAD+W+PAD][8]`，边永远是零、从不被写。
  fill 用 4 维 TAP 从整幅布局里切出每个 core 的条带（相邻条带的邻居列天然在里面，所以宽度切条不需要主机补边）；
  drain 用 TAP 写回下一层输入的内部。两个 scratch 槽乒乓（一个 `InOut` 参数），首层读 `act`，末层写 `out`。
  → 这个"统一带边布局 + TAP"是整网串联的关键，后面所有层都可以这样接。
- 4 个 core（宽 2 条 × 高 2 段），每 core 2 进 1 出 ObjectFifo，与 `conv3x3.py` 相同。
- 层间激活：内核输出 uint8（饱和=ReLU），下一层直接按 int8 读同一字节（实验约定，参考实现照做）；随机权重 ±12、shift 6，
  输出分布 10 层内稳定（均值 16–30、约一半为零），不是全零的平凡比较。

没走通/没试的：memtile 存中间激活（16ch×180×320 = 921 KB > 单个 memtile 512 KB，要跨列换 halo，复杂；DDR 方案已经够快，不必要）。

## 数字（7840HS，`python -m npu.chain_spike`，每点 50–100 次取中位）

| N 层 | 中位 ms | 最快 ms | 主机 CPU ms/次 |
|---|---|---|---|
| 1 | 0.46 | 0.42 | 0.15 |
| 2 | 0.71 | 0.67 | 0.14 |
| 5 | 1.42 | 1.36 | 0.17 |
| 10 | 2.69 | 2.51 | 0.24 |
| 20 | 4.94 | 4.78 | 0.28 |
| 40 | 9.57 | 9.32 | 0.34 |
| 85 | 19.77 | 19.32 | 0.35 |

- 拟合 N=1..20：T(N) = **0.25 + 0.236·N ms**（最快值 0.21 + 0.229·N）；带上 40、85：0.50 + 0.227·N。线性很好，没有随 N 恶化。
- **纯计算**（`--compute`：内核每行重复调 r=1/2/3 次，对 r 求斜率）：**0.193 ms/层** = 132.7 MMAC → 约 690 GMAC/s（4 core，约峰值 1 TMAC/s 的 2/3）。
- **每层额外开销** = 斜率 − 纯计算 = 0.236 − 0.193 ≈ **0.043 ms**（最快值 0.034）；用 reps 截距法算 (0.760−0.291)/9 = 0.052（最快 0.039）。
  这部分是：层间屏障（等 4 路 drain 完成 → 控制器下发下一层 BD）+ 流水线灌满（前 3 行）/排空（最后几行）。
- **每次调用固定开销** ≈ 0.2–0.25 ms（XRT 派发 + Python）。

## 对整网的推算

85 个卷积 × ~0.045 ms ≈ **3.8 ms 额外**；计算 1.84 GMAC 按本内核效率 ≈ 2.7 ms，1×1 / depthwise / stride 2 / 低分辨率层效率更低，
估 3–5 ms；加固定 0.25 ms → **约 7–9 ms/帧**，落在 6–10 ms 预期内；CPU 每帧 ~0.3 ms（比 780M 路线的 +1.8 ms/帧低）。
小层的灌满/排空更短，额外开销可能低于 0.045；还可以靠把逐元素算子（sigmoid/hardswish/残差加）融进卷积尾部来减少"层"数。

因为过了判据，"只把最重几层放 NPU"的混合方案不推荐：那要每帧在 780M 和 NPU 之间来回搬数据、同步，两边都醒着，省电效果最差。

## 本实验没回答的、下一个最大未知：异构层

这里 N 层**形状完全相同**（同一个内核、同样大小的 ObjectFifo）。真实网络每层形状不同，而：
- ObjectFifo 元素大小是编译期的，每个 compute tile 只有 2 进 2 出 DMA 通道 → 不能给 85 种形状各开 fifo；
- core 程序内存只有 16 KB → 不能实例化几十个不同 `-DWT/-DICB` 的内核。

建议下一个 spike（在泛化卷积之前做）：**"通用内核 + 运行时层描述符"**——
固定大小的块 fifo（如每块若干行 × 最大宽度，或固定字节数），每层的 IC/OC/W/stride/shift 写在权重流的头部由内核运行时读取，
DMA 侧用 TAP 按层切块；先验证 2–3 种不同形状（如 180×320 16→16、90×160 32→32 stride 2、1×1）串在一次调用里仍逐字节一致、
每层额外开销仍 ≤ 0.1 ms。通过后再按原路线：整数参考模型 → 泛化卷积 → 其他算子 → 整网接 studio。
