# RVM 整网上 NPU：高通道层的 OC / IC 分块（tiling spike）

日期 2026-11-11，分支 `phase2-npu`，未提交。接 `rvm-npu-c16-spike.md`。
代码：`npu/chain_c16.py`（规划器改成"步骤"模型）+ `npu/kernels/conv_c16.cc`（加了部分和累加/收尾）。
`npu.check` 加了 `chain_c16 deep 13 层`，完整 11/11 通过。

## 结论（一句话）

**正确性过了，开销没过。** RVM 编码器 12×20 段的 13 个真实形状层（240/480/672/960 通道的 1×1，加 Conv_176/181 的
3×3 128 通道）串成一条链，拆成 241 步，**逐字节一致**；原来"放不下"的 23 层（42% 计算）现在都能跑了。
但这一段每层额外开销 **0.2–0.3 ms**，超过 0.1 ms 判据。原因已经定位：权重 fifo 深度 1、每步计算太小（见下）。

## 做法："步骤"模型

一个权重元素 = 一步；core 外层循环按步走，每步的权重头说这一步干什么。三种层：
- **full**：整层一步（原来的样子）。
- **oc**（权重 > 18 KB）：按输出通道组切成 n_ob 块，每块把**同一份输入再喂一遍**。fill 的 TAP 最外维步长 0、重复 n_ob 次
  （还是一个 BD）；drain 最外维按块跳通道组（一个 BD）。
- **ict**（只用于 1×1，一行输入放不进 7680 B 的输入元素）：每步只带 ≤ 10 个输入通道组。部分和存在 core 本地的 int32 acc
  （IRON `Buffer` 作为 Worker 参数），权重头 `first/last` 决定从零开始还是接着累加、写回 acc 还是量化输出。
  core 上加了两段平衡循环：累加段（每行 acquire 1/release 1，不出输出，输出参数给一个 dummy Buffer）和收尾段。
  acc 只有 3 个块（7.5 KB），12×20 每 core 3 行 → OC 每份只能 1 个通道组 → 输入要按 OC 份数重读。
- 输入元素 6144 → **7680 B**（= 10 组 × (40+8)·16），这样 160 通道的 1×1（Conv_132/146）整行放得下，只需 OC 分块；
  单 core 内存约 57.5 KB（输入 4×7.5 + 权重 18.1 + acc 7.5 + 输出/dummy 1.9）。
- core `.text` 6224 B（多了两段），仍然恒定。

## 踩到的坑：一个 task group 里同一 shim 通道排太多 DMA 任务会挂死

IC 分块的层每 core 每份 OC 一个 fill BD：5 个没事，7 个以上 → `ERT_CMD_STATE_TIMEOUT`（像是 shim 通道任务队列的深度限制）。
改法：一层按 OC 份数分组，每组一个 task group，每通道每组最多 `FILLS_PER_TG = 4` 个 fill。

## 为什么慢（下一步就改这里）

1. **权重 fifo 深度 1**：每步都要等这一步的权重 DMA 到了才能算，算的时候不能预取下一步。12×20 每 core 只有 3 行，每步计算只有几 µs，
   盖不住权重加载。→ 权重 fifo 改深度 2（要省出 18 KB：把 W_MAX 降到 ~9 KB，3×3 128 通道改成 3×3 也走 IC 分块；或者输入 fifo 深度 4→3）。
2. **低分辨率层不该按空间切给 4 个 core**：12×20 的层切成 4 段 × 3 行，每个 core 都要拿**全部权重**（4 份 DMA），每步计算又小。
   → 低分辨率高通道层改成 **按 OC 切给 4 个 core**（每 core 处理全部 12 行、1/4 的输出通道）：每 core 权重流量 /4，每步计算 ×4，
   步数 /4，acc 按行数也够（12 行 × 1 块 = 12 块 … 需要 30 KB，要么 acc 只放一行、按行收尾，要么 ict 时每步只处理一行）。
3. **宽 20 补成 40**：12×20 的层一半算力花在补出来的列上（输出写 0）。CW 改成 20 或 24（8 的倍数要求要放宽到 4）能省一半。
4. 每层多个 task group 的屏障（Conv_131/144 各 3 组）。

预期 1+2 做完，deep 段每层额外应能回到 ~0.05 ms 量级，纯计算也会因为 3 降一半。

## 第二轮：定位 + 两处修改（2026-11-12）

### 先定位（前面"为什么慢"里的猜测有一半是错的）

- **单层计时会骗人**：单层调用里固定成本占大头，看不出层在链里的真实代价。改用"deep 链逐层加前缀"测**边际**耗时。
- 第一轮的边际：IC 分块层最贵（Conv_144 +0.75 ms、Conv_163 +0.61、Conv_131 +0.44），同 MAC 的 OC 分块层（Conv_146）只要 +0.23。
- 对照实验：acc 加倍（每份 2 个通道组、输入重读减半）只快 8%；权重 fifo 深度 2（预取）**没有变化**。
  → 不是"权重没预取"，主要是**每步搬了太多没用的输入**（12×20 存成 40 宽，每块读 768 B，真实只要 20 像素）+ 每个 core 都拿全部权重。

### 修改 1：补宽列不算也不读

内核里整组 8 像素都在有效宽度之外时只写零、不做乘加；主机按"有效宽度向上取 8"定 PLANE（12×20 → 每块 512 B，原来 768）。
一个输入元素能放 15 个通道组（原来 10）→ 240/208 通道的 1×1 不用 IC 分块了，其余 IC 分块步数降约 40%。总步数 241 → 164。

### 修改 2：低分辨率 OC 分块层改成 OC 并行

宽 ≤ 40（一条带）的 OC 分块层：每个 core 算不同的 OC 块（c, c+4, …）、处理全部 12 行，只拿 1/4 的权重。
权重缓冲区改成 [槽][core] 存（每个 core 一份，空闲槽是全零头），e_w 补到 256 的倍数，fill 写成 `[槽][e_w/256][256]`
（交错存放后 DMA 不能当连续段，最内维受 1023 字限制）。槽数 164 → 132。core `.text` 6288 B，仍恒定。

|---|---|---|---|
| deep 整链 最快 / 中位 | 3.92 / 4.29 ms | 2.67 / 3.23 | **2.43 / 2.57** |
| 每层额外（reps 拆分，最快/中位） | 0.22 / 0.30 | 0.12 / 0.14 | **0.12 / 0.105** |

逐层边际（修改 1+2 后，ms）：Conv_68 +0.04、Conv_74 +0.04、Conv_92 +0.11、Conv_104 +0.17、Conv_105 +0.12、
**Conv_131 +0.36**、Conv_132 +0.19、**Conv_144 +0.38**、Conv_146 +0.21、**Conv_163 +0.32**、Conv_176 +0.20、Conv_181 ≈0。
enc / low 两条链不受影响；`npu.check` 11/11。

### 还剩什么

4 个 IC 分块层（Conv_104/131/144/163）占 deep 链的一半（1.23 ms）：每 core 3 行、acc 只够每份 1 个通道组 → 输入按 OC 份数重读 7–10 遍。
可选的下一步：
1. 省出内存把 acc 放大（3×3 128 通道那两层也走 IC 分块，W_MAX 从 18 KB 降到 9 KB → acc 可以到 6 块）→ 输入重读减半；
2. IC 分块层的输入元素去掉左右 PAD（1×1 不需要）→ 每块 320–384 B，一个元素放 20 组；
3. 更根本：用 memtile（每列 512 KB）缓存 12×20 的整张激活 / 整层权重，重读从 memtile 走而不是 DDR。
